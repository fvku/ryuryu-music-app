## 依頼1（着手前に必要）：`item.source` の更新経路

保存API（`PATCH /:id`、`kind: "item"`）が受け取るのは `content` だけで、`source` を更新できません。
Release Master側で `画像リンク変換` ／ `spotifyカバー` が差し替わっても `source.coverUrl` が古いままになります。

2026-09-11にも申し送った問題ですが、v2ではフローの1段目が「カバージャケットを取り込む」を含むため、
**この経路が無いとフローが成立しません。**

考えられる形は3つです。どれを採るかはお任せします。

1. `generator_reimport` を拡張し、既存作品の `source` も更新対象にする（作品の追加・削除と同じversionで確定）
2. `PATCH` に `source` を受け取る経路を足す（対象別ロック・`expectedVersion` は現状のまま）
3. `source.coverUrl` だけを更新する専用の対象種別を足す

利用者が手でアップロードしたジャケット（`content.jacketAssetId`）を、この更新で消さないことだけ必須です。

## 依頼2：画像ごとの保存で途中失敗したときの扱い

「画像ごとに1つの保存ボタン」にします。内部は、その画像の作品（掲載なら最大2件、Other Releasesなら最大60件）と
背景色に対して対象別PATCHを順に呼びます。DB契約は変えません。

複数対象をまとめて確定する経路が無いため、途中で失敗すると一部だけ確定した状態になります。
こちらの案は「成功した分は確定したまま残し、失敗した対象名を出して再試行させる」です。
全体ロールバックはAPIが持っていないので行いません。

- この扱いで問題ないでしょうか。
- Other Releasesは1画像に最大60作品あります。連続PATCHの上限・間隔の目安があれば教えてください。
- まとめて確定するRPCを足す判断があるなら、UI側はそちらへ寄せます。

## 依頼3：Weeklyの並びを区分別に分岐させる

Weeklyの並びを、採用（メイン）はRelease Masterの行順、Other Releasesは従来規則にします。
**初回の取り込みと取り込み直しで同じ規則**にしたいです。初回と更新で並びが変わらないようにするためです。

- 現在、採用側は `sortAlbums`（EP区分 → 日付 → アーティスト名）を通っています。これを行順へ変えてください。
- Other Releasesの `sortWeeklyOthers`（洋楽アルバム → 邦楽アルバム → EP、各区分内はアーティスト名順）は維持します。
- 影響するのは `lib/generator/source.ts` の `selectWeeklyAlbums`（初回）と、
  `lib/generator/reimport.ts` の `resort`（更新）の両方です。
- `sortAlbums` はMonthly／Japanの並べ直し専用として残ります。
- 既存文書の並びは `itemIds` に固定されているので変わりません。ここは従来どおりで構いません。

## 依頼4：作品集合をまたぐ並び順の復元の説明

現在、作品の追加・削除をまたぐ `structure` の復元は拒否で確定しています
（UI側は `latestReimportVersion` 以降の版しか選択肢に出していません）。

v2では版の表示を画像単位に組み替えるので、「この画像の過去版へは戻せるのに、
並び順だけ戻せない版がある」という見え方になります。
この制約の説明の仕方、またはDB側で作品集合の差を扱えるようにするかどうかを相談させてください。
こちらの案は、選択肢から外したうえで「作品の増減より前の版には戻せない」と理由を出すことです。

## こちらで並行して進めること

回答を待つ間、UI側は次を進めます。API payloadは変えません。

- 共通設定を編集画面のタブから外し、`/generator/<id>/settings` へ分離する
- 「Release Masterから再取得」と「Release Masterから取り込み直す」を1つの差分ダイアログへ統合する
- 版表示を画像単位へ組み替える。文書の通し番号は履歴画面にだけ残す
- 保存ボタンを画像ごとに1つへ束ねる（依頼2の回答までは、成功分を残す案で実装する）
- 背景色の自動抽出をブラウザ側で実装する。サーバー・DB・保存形式は変えない
