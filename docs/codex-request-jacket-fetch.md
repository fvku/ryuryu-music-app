# Codexへの依頼文（そのまま貼って使う）：CORS非対応の配信元から画像を取り込む

作成日：2026-09-13（Claude Code）。元の記載は `docs/codex-generator-handoff.md` の
「依頼：CORS非対応の配信元から画像を取り込む経路」。

---

`ryuryu-music` の画像ジェネレーターで、ジャケット画像の取得元に制限があることが実データで分かりました。
サーバー側の対応をお願いしたい件が1つと、判断してほしい件が1つあります。
UI側はAPIも保存形式も変えていません。

## 何が起きたか

利用者の指示で「ジャケットが無いときはアップロードと画像URLの貼り付けの両方を使えるように」を実装しました。
貼り付けは、ブラウザで画像を読んでJPEGにし、既存の `jacketAssetId`（非公開Storage）として保存する形です。

これが Bandcamp の画像で失敗しました。実測は次のとおりです。

```
curl -sI -H "Origin: http://localhost:3000" https://f4.bcbits.com/img/a0712120107_10.jpg
HTTP/2 200
content-type: image/jpeg
content-length: 113659
（access-control-* は返らない）
```

描画コアは `image.crossOrigin = "anonymous"` で読みます（`app/generator/runtime.tsx`）。
canvasを汚染させずPNGを書き出すために必要な指定なので外せません。
したがってこの配信元はブラウザから1バイトも読めません。

## 影響は貼り付けだけではありません

同じ理由で、**Release Master の `画像リンク変換` 列に Bandcamp のURLを入れても描画できません**。
ジャケットが空のまま出て、PNGにも入りません。
「画像リンク変換の充足率が高い」という前提は、そこに入るURLが CORS を許す配信元
（Apple Music・Spotify）である限りで成り立っています。

## 依頼1：サーバー側でURLを取得して保存する経路

案として、`POST /api/generator/documents/:id/assets` に、ファイルの代わりに `url` を受け取る形を足す方向です。
実装の形はお任せします。

- 既存の検査（`lib/generator/image.ts` の MIME・マジックバイト・寸法・10MB／40MP）をそのまま通したいです。
  ヘッダーの `content-type` は信用せず、取得したバイト列で判定する現在の方針のままで構いません。
- 対象のロック（`kind: "item"`、`clientId`・`token`・`generation`）は今と同じように要求してください。
- SSRF対策が必要です。https のみ、私設・リンクローカル・ループバックのアドレスを拒否、
  リダイレクト先も同じ条件で再検査、応答サイズの上限、タイムアウト、資格情報を送らない。
- 取得したバイトをそのまま保存できると嬉しいです。ブラウザ経由だと JPEG への焼き直しになります。

## 依頼2（判断）：描画側のカバー取得をサーバー経由にするか

`画像リンク変換` に CORS 非対応のURLが入っている行は、いまは描画もPNGも通りません。
画像を中継するルートを置けば解決しますが、外部取得の常時経路になるため影響が大きいです。
UI側の判断ではなく、機能側で決めてください。

## それまでの回避策

画像を保存してから、ジャケット欄のファイル選択でアップロードする方法は今も通ります。
貼り付けが失敗したときは、理由とこの手順を画面に出すようにしました。

作業ブランチは `feat/generator-flow-v2` です。
