## 3. 保存とロックの設計案

### 企画・アルバム・ページを分ける

文書は `series + period_type + period_start + period_end` を持つ。月次／週次と表示名を区別し、対象期間とRelease Masterの抽出条件も別に保存する。企画IDと期間識別子に一意制約を設ける。Weeklyの週境界は未決定で、ISO週番号だけに固定しない。

アルバム項目には文書内の安定IDを採番し、Release Master UIDを別に保持する。ページ番号や配列位置を識別子にしない。UID欠落時はtitle+artistの一意候補だけを使用し、曖昧な場合は選択を求める。

掲載2件が同じ画像に入るため、アルバム項目とページを分ける。ページは安定ID・表示順・所属項目ID・背景色を持つ。旧データのページ上側の色を、移行時にページ色へ移す。並び替え後も色はページ枠に残す案を推奨するが、旧動作との差なので承認事項にする。変更前後の組合せ・色を並び替えプレビューで確認できるようにする。

### 最小構成の更新: 5テーブル＋非公開バケット

当初の3テーブル案から、3人の部分更新と対象別ロックのために分離する。

| テーブル | 保存内容 |
|---|---|
| generator_documents | 企画・期間、取り込み条件、ページ構成、共通波／背景、出力設定、文書版、構成版・共通設定版 |
| generator_items | 安定項目ID、文書ID、RM UID、取り込み元スナップショット、fields・show・tracking・kerns・手動画像参照、項目版、更新者 |
| generator_locks | 文書・対象種別・対象IDの一意キー、所有者、画面識別子、世代、トークンハッシュ、期限 |
| generator_revisions | 文書版、変更対象、作者・日時・種別、復元元、再送判定ID、版時点の全編集状態と画像参照 |
| generator_assets | 文書ID、Storageパス、ハッシュ、寸法・形式、由来、作成者、pending／ready状態 |

ページや共通設定は文書内の構造化データで保持し、初期版からページテーブルまでは増やさない。項目版・ページ設定版・構成版は独立させる。

全編集項目の必須保存対象は、作品名（手動改行を含む）、アーティスト名、曲数総尺、ジャンル、国、選曲番号、曲名、本文、各帯の表示／非表示、採用・掲載の区分と順序、ページ背景色、波画像、合成済み背景画像、手動ジャケット、本文全体字間、文字位置別カーニング、出力サイズ。フォント・描画処理・保存形式の版と取り込み元の値も残す。

Imageオブジェクト・一時blob URL・署名付きURLは永続データにしない。選択中のページ・スクロール位置等は利用者ごとのローカルUI状態として分離する。

### 編集対象ごとのロック

| 対象 | 排他範囲 |
|---|---|
| アルバム項目 | 本文・各項目・ジャケット・表示設定・本文全体字間・文字別カーニング |
| ページデザイン | そのページの背景色。掲載上下2件の本文編集は並行可能 |
| 共通デザイン | 企画共通の波画像・合成済み背景・共通出力設定 |
| 構成 | 採用／掲載順、ページ再配置・追加・削除・再取り込み |
| 全体復元 | 文書全体を一時的に編集停止し、他の対象ロックがない状態で実施 |

並び替えは本文内容を変更しない。ページ色の変更中にページ構成を変えないよう、構成操作とページデザイン操作は競合させる。削除には構成権と対象項目の非編集中確認が必要。全体復元中の新規ロック取得は拒否する。複数ロック取得は固定順・短いDBトランザクションで処理する。

### 失効と端末間引き継ぎの具体案

値は初期検証用の提案で、実機試験後に調整する。

- 「閲覧」で開き、「編集開始」で取得。対象ごとに現在の編集者を表示する。
- 生存確認は30秒ごと、有効期限は最終成功から3分。サーバー／DB時刻で判定する。
- 保存・延長・解放は所有者、画面ID、トークン、世代を照合する。期限を過ぎたロックは延長で復活させない。
- 「保存して編集終了」を交代の基本操作にする。
- 前面で15分無操作なら継続確認を表示し、60秒応答がなく全入力が共有保存済みの場合に解放する案。未保存データを破棄する理由にはしない。
- 画面非表示・アプリ切替時にはローカルへ直ちに退避し、共有保存は可能な範囲で試みる。終了イベントでの通信成功には依存しない。
- バックグラウンドの生存確認継続は保証しない。復帰時にロックと最新版を取り直し、その確認前には編集を再開しない。
- 通信断ではローカル下書きを保護し、共有編集を停止。再接続後、項目版が同じなら取得し直して再開できる。他人が変更済みなら差分確認を挟む。
- 自分の別端末へは「この端末へ引き継ぐ」を明示操作とし、新しい世代へ更新する。旧端末の保存は拒否する。旧端末の未送信下書きが自動で移るとは約束しない。
- 別の人の有効ロックの強制解除は初期版に設けない。交代希望のアプリ内表示は第2段階候補とする。

### 部分保存と履歴

ブラウザは変更対象だけを送る。サーバーは対象版・対象ロックを確認し、最新の他項目を保持したまま更新する。文書全体の古いJSONを受け取って上書きしない。別項目の更新で文書版が増えただけなら、項目保存を競合扱いにしない。

保存は1回のDBトランザクションで、対象更新・版更新・全状態の履歴追加を完了する。文書行の短いDBロックで履歴の順序を確定するが、人間の編集時間中にDB接続を占有しない。再送IDは文書内一意とし、応答消失時には既処理結果を確認できる。保存要求はクライアント内で対象ごとに直列化する。

自動保存の初期案は入力停止2秒後、連続入力中でも最大15秒程度ごと。日本語IMEの変換途中は無理に共有確定せず、変換確定を待って送る。ローカル退避はより頻繁に行う。

項目復元はその項目だけを現在の状態へ適用し、他人の編集を維持して新しい文書版を作る。ページ色の復元と本文復元は分ける。履歴は削除せず、参照画像も保持する。全体復元は全員の編集終了後。全体版履歴と、利用者のUndo／Redoは分ける。

IndexedDBには、アカウント・文書・項目・端末ごとの下書き、元の項目版、未送信画像を保存する。別アカウントの下書きを自動表示しない。古いサーバー応答で、入力中の新しいローカル状態を巻き戻さない。

## 4. 認証・RLS・画像の境界

既存のGoogle認証を利用し、許可判定の優先順位を変えずに共通関数化する。ジェネレーターではページ・API・画像取得すべてで許可一覧を再確認する。Googleを入口にするための認証元・確認済みメール情報を保存し、既存セッションにその情報がない場合の再ログインを設計する。Spotify接続がなくても画像作成できる。

Supabase Authを別に導入せず、ブラウザはNext.js経由でDBへアクセスする。5テーブルのRLSを有効にし、anon／authenticatedの直接アクセス権限を撤回する。DB関数はPUBLICを含む不要ロールからの実行を拒否し、サーバーだけに許可する。service roleはRLSを迂回するため、利用者の認可はサーバー、ロック・版検証はDB関数で必須化する。[Supabase公式RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

Release Masterはサーバー専用の読み取り処理から取得する。統合後の同一アプリ内部で自分の公開HTTP APIへBearer付きで折り返すことを必須にしない。既存のSheets取得を再利用できるか、最新のマージ済みコードで確定する。APIキー・Google資格情報をNEXT_PUBLIC変数、HTML、ブラウザ保存、ログに出さない。認証情報を含むエラーの生出力も禁止する。

Storageは非公開。画像アップロードは限定された署名付き保存先へ行い、完了時に形式・サイズ・寸法・所有文書・有効ロックを再確認する。確定画像は上書き不能な別パスで保持し、発行済みアップロードURLで過去版の画像が変わらないようにする。未確定画像を参照する共有保存は成功扱いにしない。Vercel通常APIの容量制限を避ける。[Vercel容量制限](https://vercel.com/docs/functions/limitations)

手動画像と採用したジャケットは実体保存。描画用取得は認証を通す配信または短時間署名付きURLを使う。許可ホスト・リダイレクト・容量を検証し、任意URLを無制限に代理取得しない。古い履歴が参照する画像は削除しない。画像登録完了と文書保存の間で失敗した場合は未参照画像として再利用／整理できる状態にする。

## 5. 画面・API・移植方法

画面は企画一覧、アルバム編集／プレビュー、履歴／復旧パネルを中心にする。モバイルでは一覧・編集・プレビューを切り替え、保存状態と編集者名を常に確認できるようにする。

### 掲載ページの編集画面（ユーザー確認を反映）

掲載1ページには、上段アルバムと下段アルバムの**2つの独立した編集フォーム**を表示する。**背景色の指定はページ共通で1つだけ**とし、各アルバムのフォーム内には置かない。

| 画面内の領域 | 内容 | 保存・ロック単位 |
|---|---|---|
| ページプレビュー | 上下2アルバムを合成した出力画像1枚 | 保存版を固定してPNG出力 |
| 上段アルバムのフォーム | 作品名、アーティスト、曲数総尺、ジャンル、国、おすすめ曲、表示設定、ジャケット | 上段の項目ID |
| 下段アルバムのフォーム | 上段と同じ種類の入力欄。値・保存状態・編集者表示は独立 | 下段の項目ID |
| このページの背景色 | 色指定1つ。HEX・スポイド・色調整は同じ1つの値を変更 | ページID |

PCでは両フォームを同一画面内に配置し、それぞれ「上段」「下段」とアルバム名を表示する。モバイルでは上下のフォームを縦に配置し、必要に応じて折りたためる構成にする。折りたたみは表示だけの操作で、もう一方の入力・保存・ロック状態を初期化しない。ページ共通の背景色欄は重複させない。

上段をAさん、下段をBさん、背景色をCさんが並行編集できる。背景色の変更は2件を含む画像全体に反映するが、アルバムの各入力値は変更しない。ページを開くだけで上下2件のロックを一括取得しない。編集開始・保存・終了は対象ごとに行い、片方が閲覧専用でももう片方は編集できる。

掲載枠は現行仕様で評価本文を画像に載せないため、掲載フォームには本文と本文用字間・カーニングの操作を出さない。取り込み元に本文や既存の文字調整があっても、非表示を理由に保存データを削除しない。採用ページでは従来通り本文と文字調整を編集できる。

現行の静的UIは選択中の1アルバムを共通フォームに表示する実装であり、2フォーム表示は統合版で行う変更である。[現行renderForm](/Users/koheifukuda/Documents/Claude/Projects/漂流音楽/tools/monthly-generator/editor/js/ui.js:284)

波画像・合成済み背景画像は企画共通設定に置き、上下のアルバムごとに重複させない。合成済み背景が優先される場合は、ページ色が現在の見た目に反映されないことを色欄に表示する。掲載が奇数件で最終ページに1件しかない場合は、存在する1フォームと背景色1つを表示し、架空の2件目を作らない。

既存のpages.js、layout.js、textEngine.js、render.jsを出発点にする。ビルド済みHTMLを丸ごと埋め込まず、ブラウザ専用描画とサーバー専用データ処理を分離する。state.jsのメモリ上の状態を永続モデルへ移し、ui.jsのDOM直結処理をReactへ接続する。70件の既存テストは基準として引き継ぐ。

## 6. モバイルSafariとPNG

2400px出力を内部4倍で描く現行方式は9600×9600px。RGBAを1画素4バイトと仮定すると、その画像領域だけで約352MiBになる。これは計算上の下限的な目安であり、実機メモリ測定値ではない。縮小先、ジャケット、他のページ、PNG圧縮用領域が追加される。

最初の技術検証で次を比較する。

1. 大きい中間Canvasをタイルごとに描いて縮小し、最終画像へ合成する。文字の輪郭・タイル境界を基準画像で確認する。
2. 画像とサムネイルを遅延読込し、必要数だけ保持。出力は直列化し、中間Canvas・blob参照を明示的に解放する。
3. PNG生成と共有を2段階にする。生成済みファイルを、次のユーザー操作で共有する。[Web Share API](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/share)
4. どうしても端末内で品質・安定性を満たせない場合だけ、サーバー描画を別案として見積もる。無断で出力サイズや品質を下げない。

厳密なプレビューは、最終サイズの描画結果を縮小表示する方式にする。編集中の軽量表示を設ける場合は、出力前に最終プレビューを確認できるようにする。別端末間の完全なバイト一致は現在の静的仕様でも必須ではないが、同じ保存版からの改行・配置・文字調整は受入基準にする。

モバイルでは範囲選択後にボタンを触っても選択情報が失われないUI、数値入力・増減、上下移動、写真／ファイル選択、キーボードの表示領域、画面回転を扱う。写真の向き・HEIC等の入力形式は実機検証し、PNG/JPEG/WebPへの変換経路または明確な案内を設ける。

ローカル保存は容量・削除の影響を受けるので保証された共有保存として表示しない。[WebKit保存ポリシー](https://webkit.org/blog/14403/updates-to-storage-policy/)

デスクトップChrome／Brave／Edge／Safari、iPhone Safari、iPad Safariを対象表に明記し、対応OS・ブラウザ版はメンバーの実機に合わせて着手時に固定する。WebKit自動テストだけで製品版Safariの合格とはしない。[Playwrightブラウザ仕様](https://playwright.dev/docs/browsers)
