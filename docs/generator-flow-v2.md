| 論点 | 決定 | 従来 |
| --- | --- | --- |
| 背景色の取り込み | **カバーから自動抽出し、初期値として入れる** | 自動抽出はしない（2026-09-04の決定）。人がカラーピッカーで決める |

## 1. 制作フロー

利用者が想定する3段階をそのまま仕様の骨格にする。

### 1-1. 取り込む

Release Masterから次を取り込む。**初回の文書作成も、途中の取り込み直しも同じ経路**にする。

| 取り込む内容 | 現状 | v2 |
| --- | --- | --- |
| 文字情報 | 作成時のみ。途中は「再取得」で下書きへ | 同じダイアログで扱う |
| 並びの順番 | 作成時のみ | 同じ。series別の既定は §4-4 |
| カバージャケット | 作成時のみ。途中は更新できない | 途中でも更新する（§8-1） |
| カバー由来の背景色 | **取り込まない** | **抽出して初期値に入れる**（§5） |
| 作品の増減・区分 | 「取り込み直す」 | 同じダイアログで扱う |

### 1-2. 直す

画像を1枚選び、その画像について文字情報と背景色を直す。字送り、行送り、背景色はここに入る。
共通設定（波、合成背景画像、出力サイズ）は画像に属さないので、この導線から外す（§2）。

### 1-3. 書き出す

1枚ずつのPNGと、全ページのZIP。判定条件（文書全体に未保存があると止める、はみ出しで止める）は変えない。

## 2. 画面構成

```
/generator                    企画一覧・作成
/generator/<id>               画像の編集（情報修正 ／ 背景設定）
/generator/<id>/settings      共通設定（波・合成背景・出力サイズ）
/generator/<id>/history       変更履歴
```

- 編集画面の編集パネルは**「情報修正」「背景設定」の2タブ**になる。「共通設定」タブを外す。
- 共通設定はヘッダーからの遷移にする。文書に1つしかなく、画像を選んでいる状態と無関係なため。
- 並び順は現状どおりモーダル。編集画面のタブを増やさない。
- 3カラム（サムネイル／大プレビュー／編集パネル）と1280px未満のsticky、
  編集画面だけボトムナビ・フッターを出さない判定（`isImmersiveRoute()`）は変えない。

## 3. 版と保存の単位

### 3-1. データ側は現状のまま

共有DBはすでに対象ごとに版を持っている。ここは**変えない**。

| 対象 | 版 | 粒度 |
| --- | --- | --- |
| 作品 | `itemVersions[itemId]` | 作品1件 |
| 画像の背景 | `pageVersions[pageId]` | 画像1枚 |
| 共通設定 | `themeVersion` | 文書1つ |
| 並び順 | `structureVersion` | 文書1つ |
| 文書 | `version` | 上のどれかが動くたびに1つ進む通し番号 |

「版管理を画像ごとにしたい」という要望は、**DBの側ではすでに満たされている**。
分かりにくいのは表示だけで、ヘッダーの `version 12` が文書の通し番号であり、履歴もその通し番号で並ぶため、
画像ごとに版が付いているように見えない。

### 3-2. 画像と作品は1対1ではない

| 画像の種類 | 作品の数 | 背景色 |
| --- | --- | --- |
| 採用（Monthly／Japan） | 1 | 画像に1つ |
| 掲載（Monthly／Japan） | 1〜2（上段・下段） | 画像に1つ（上下共通） |
| 表紙（Weekly） | 0 | 画像に1つ |
| メイン（Weekly） | 1 | 画像に1つ |
| Other Releases（Weekly） | 1〜60 | 画像に1つ |

したがって「画像の版」は、内部的には**その画像に載っている作品の版と、画像の背景の版の束**になる。

### 3-3. UIでの見せ方

- ヘッダーの版表示を**選択中の画像**のものに変える。`画像 3 · 最終保存 2026-09-12 18:20 · Kohei`。
- 文書の通し番号は履歴画面にだけ残す。編集画面のヘッダーからは外す。
- サムネイルには現在も出している未保存・他の人が編集中・背景未設定の3状態を維持する（`derivePageBadges()`）。

### 3-4. 保存ボタンを画像ごとに1つへ

いま開いている画像の「保存」1つで、**その画像の作品（複数可）と背景色**を確定する。

- 内部は対象別PATCHの連続呼び出し。ロックも版も対象別のまま。**DB契約は変えない。**
- 送るのは、その画像のうち**下書きが変わっている対象だけ**。変わっていない対象にはPATCHを出さない。
- 途中で失敗した場合の扱いは §8-2（Codex確認事項）。現時点の案は「成功した分は確定したまま残し、
  失敗した対象名を出して再試行させる」。全体ロールバックはAPIが持っていないため行わない。
- 共通設定と並び順は、それぞれの画面・モーダルの中に保存を置く。画像の保存とは混ぜない。

## 4. Release Masterからの更新

### 4-1. ボタンを2本にする

| ボタン | 何をするか |
| --- | --- |
| **最新版に更新** | 共有DBの最新スナップショットを取り直す。他の人の保存を取り込む。自分の未保存下書きは破棄される。Release Masterは見ない |
| **Release Master 再読込** | Release Masterを読み直し、作品の増減・区分移動・文字情報・カバー画像の差分を1つのダイアログで選ばせる |

現在の「Release Masterから再取得」（文字情報だけ）と「Release Masterから取り込み直す」（作品の増減だけ）を
**1本に統合する**。Release Master側の変更は利用者から見れば1つの出来事であり、
2つに割れているのはAPI都合（`PATCH` と `reimport` RPC）でしかない。APIは2本のまま、UIだけ1つにする。

「Release Master 再読込」で差分を見る操作は読み取り専用であり、ロックを取らない。画像を編集中でも確認でき、
その画像のロックも維持する。作品の増減・区分移動・並べ直しを実際に確定するときだけ、自分の画像ロックを返して
`structure`ロックを取る。他の利用者が画像を編集中なら、差分は見せたまま確定だけを待たせる。
文字情報・カバー差分をローカル下書きへ入れるだけなら`structure`ロックは不要。

### 4-2. 差分ダイアログ

4区画に分けて、画像番号の順に並べる。

1. **増える作品**。Release Masterで採用／掲載になったが文書に無いもの。既定ON。
2. **消える作品**。区分を外された、または行が消えたもの。**手を入れていない作品だけ既定ON**。編集済みは「手で修正済み」を出して既定OFF。
3. **区分の移動**。採用↔掲載、メイン↔Other Releases。既定ON。
4. **文字情報の差分**。作品ごと・項目ごと。取り込み時の値のままの項目だけ既定ON。手で直した項目は既定OFF。
   比べるのは**その画像に描かれる項目だけ**（§26の決定を維持）。

末尾に並べ直しのチェック（§4-4）と、実行後の枚数を出す。

### 4-3. 実行の順序

1. 未保存の下書きがあっても実行できる（2026-09-13に変更）。既存作品の内容は取り込み直しで変わらないので、
   生き残る作品の下書きはそのまま引き継ぐ。外れる作品のぶんだけ破棄し、実行前に削除の行へ「未保存あり」を出す。
2. 1〜3（作品の増減・区分移動）を `reimport` で**1つの新しいversionとして確定**する。
3. 返ってきたスナップショットで全体を差し替える。
4. 4（文字情報）とカバー画像を**ローカル下書きへ入れる**。確定は画像ごとの「保存」。
5. 新しく増えた画像・作品については、背景色の初期値を抽出して下書きへ入れる（§5）。

2 と 4 で確定のされ方が違う点は、ダイアログの中で明示する。
「いま確定するもの」「保存待ちになるもの」を区画の見出しで分ける。

### 4-4. 並び順の追従

2026-09-12の決定。**初回の取り込みと取り込み直しで同じ規則を使う。** 初回と更新で並びが変わらないようにする。

| 対象 | 並び |
| --- | --- |
| Monthly／Japan（採用・掲載） | 並べ直さない。チェックを入れた場合だけ `sortAlbums` で並べ直す |
| Weekly 採用（メイン） | **Release Masterの行順に追従する** |
| Weekly 掲載（Other Releases） | **従来規則を維持する。** 洋楽アルバム → 邦楽アルバム → EP、各区分内はアーティスト名順（`sortWeeklyOthers`） |

したがって `sortAlbums` はWeeklyの採用では使わなくなり、Monthly／Japanの並べ直し専用になる。
`sortWeeklyOthers` はOther Releasesで初回・更新とも使い続ける。

既存作品は作品IDのまま並び替わるので、直した文字・ジャケット・字間・行送り・履歴はすべて保持される。

## 5. 背景色の自動抽出

### 5-1. いつ抽出するか

- 新しく作品が入った画像。初回の取り込み、取り込み直しでの追加、区分移動で新しく作られた画像。
- 利用者がジャケットを差し替えたとき。

**人が一度決めた背景色は上書きしない。** 抽出は `bgColor` が未設定（`null`）の画像に対してだけ行う。
差し替え時は、上書きせずに「抽出した色に変える」ボタンを背景設定へ出す。

### 5-2. 何から抽出するか

画像に複数の作品が載る場合は**先頭の作品**のカバーを使う。掲載なら上段、Other Releasesなら1件目。
Weeklyの表紙は作品を持たないので、メインの1枚目のカバーを使う。

### 5-3. どこで抽出するか

色の抽出処理はブラウザ側で行う。Release Master由来の外部カバーは、2026-09-13以降は認証付きの
同一Origin APIを経由して読むため、配信元がCORSを許可しない場合もcanvasから画素を読める。

- DB・背景色の保存形式は変えない。抽出結果は通常の `bgColor` として下書きへ入り、画像の「保存」で確定する。
- 抽出に失敗した場合（URLの応答失敗、画像形式不正など）は、現在と同じ「未設定」のまま仮の色で描く。抽出の失敗で操作を止めない。

### 5-4. どう抽出するか

この版面は「色の面 ＋ 波（Luminosity・不透明度50%）」の合成で、白文字を載せる前提になっている。
したがって抽出した代表色をそのまま使うと、明るいジャケットで文字が読めなくなる。方針だけ先に決める。

1. カバーを32×32程度へ縮小し、色を量子化して最頻の色群を出す。
2. 無彩色に近い群（彩度が極端に低い）と、白飛び・黒潰れの群を候補から外す。
3. 残りから面積の大きい群を代表色とする。
4. 白文字が読める範囲へ明度を寄せる。具体値は過去の投稿実物と突き合わせて決める（§9-2）。

**抽出値はあくまで初期値**で、人がカラーピッカーで直せることは変わらない。

## 6. 編集の開始とロック

利用者の決定により、**「編集」ボタンを押してから編集する形に戻す**。

- 編集画面を開いただけではロックを取らない。画像ごとの「この画像を編集」を押した時点で、
  その画像の作品ロックと背景ロックをまとめて取得する。
- 保存後もロックは保持する。続けて直せるようにするため。明示的な「編集を終了」で解放する。
- 別の画像の「編集」を押したときは、前の画像のロックを解放する。見て回るだけで複数を占有しない。
- 共通設定と並び順は現状どおり明示的な編集開始。これで4対象すべての開始方法が揃う。
- 他の人のロック、自分の別端末のロック、取得失敗の表示と引き継ぎ・再試行は現状のまま維持する。
- 30秒heartbeat、3分失効、`clientId` ／ `token` ／ `generation` の照合は変えない。

## 8. Codexへ確認・依頼する事項

1. **カバー画像の更新**。`item.source.coverUrl` と `source.fields` は取り込み時のスナップショットで、
   `PATCH`（`kind: "item"`）は `content` しか受け取らない。Release Masterでジャケットが差し替わったときに
   追従する経路が無い。`reimport` で既存作品の `source` を更新できるようにするか、
   別の対象種別を足すか。**UI側だけでは解決できない。**
2. **画像ごとの保存の途中失敗**。作品と背景を続けてPATCHする間に片方が失敗した場合の扱い。
   現在のAPIには複数対象をまとめて確定する経路が無い。案は「成功分は残し、失敗した対象を再試行させる」。
   まとめて確定するRPCを足す判断もあり得る。
3. **Weeklyの並び**。採用は行順、Other Releasesは `sortWeeklyOthers` という区分別の分岐を、
   `selectWeeklyAlbums`（初回）と `reimport` の `resort`（更新）の両方へ入れる必要がある。
   現在は採用側が `sortAlbums`（EP区分 → 日付 → アーティスト名）を通っている。
4. **作品集合をまたぐ並び順の復元**。現在は拒否で確定している（`latestReimportVersion` 以降しか選べない）。
   画像ごとの版表示にしたとき、この制約をどう説明するか。

### 8-1. Codex判断・実装：`item.source`はitem PATCHで保存する

3案のうち **2** を採用する。`PATCH /:id` の `kind: "item"` は、従来必須の `content` に加えて、
Release Master由来の完全な `source` を任意で受け取る。両者を同じitemロック・`expectedVersion`・`requestId`で
原子的に保存し、item versionと文書versionを1つずつ進める。これにより、文字とカバーをローカル下書きへ入れ、
画像の保存時に確定する §4-3 の順序を維持できる。`reimport`で先にsourceだけを確定する方式にはしない。

- `source.kind` は `release-master` だけを更新可能とし、全項目を既存の文書型で検証する。手動作品のsourceは変更しない。
- sourceを含むPATCHだけは新しい`generator_item_save` RPCへ送る。未適用DBがsourceを無視してcontentだけ保存することを防ぐ。
- DBでも、同じ文書内の空でないUID重複を拒否する。
- `content.jacketAssetId` はsourceと別に保存するため、カバーURL更新では消えない。
- itemの過去版復元は、以後 `content` と `source` を同じ対象として復元する。
- 適用済みSQLは変更せず、`202609120001_generator_item_source.sql`を追加した。2026-09-12に共有DBへ適用済み。

### 8-2. Codex判断：画像保存は部分成功を許容する

新しい一括保存RPCは追加しない。対象別ロック・対象別version・対象別履歴という既存契約を優先し、
成功した対象は確定したまま残す。UIは成功対象を保存済みへ更新し、失敗対象名だけを残して再試行させる。

- Other Releasesは最大60作品＋背景1件を、同時実行数1、呼び出し間の固定待機0msで順にPATCHする。
  現行APIにこれより小さい件数上限・レート制限は設けない。
- 2xxごとに返却snapshotを反映し、次の対象の`expectedVersion`はその最新snapshotから取る。
- 4xxの対象別競合は失敗として表示する。認証・認可エラーは残りも成功しないため中止する。
- 通信断・5xxは確定済みか不明なので、その対象で列を止める。同じ本文と`requestId`で結果を確定してから再開する。

### 8-3. Codex実装：Weeklyの並びを区分別にした

初回の`selectWeeklyAlbums`は採用をRelease Masterの入力行順のまま返す。取り込み直しの`resort: true`も、
Weeklyのfeatureだけは同じ行順にする。Other Releasesの`sortWeeklyOthers`と、Monthly／Japanの`sortAlbums`は維持する。
既存文書の`itemIds`は変更しない。

### 8-4. Codex判断：作品集合をまたぐstructure復元は拡張しない

DBの集合一致検査と`latestReimportVersion`による候補除外を維持する。過去の作品集合を復元する操作は、単なる並び順の復元ではなく、
作品・ページ・ロック・画像参照を再作成／削除する別操作になるため、この導線には混ぜない。

UIの説明は次を基準にする。

> 並び順は、最後に作品を取り込んだ時点以降の版へ戻せます。作品の増減より前の版は、当時と作品数が異なるため選べません。
> 過去の作品構成へ戻す場合は「Release Master 再読込」で内容を確認してください。

## 10. 変えないもの

- 描画結果、PNG／ZIPの出力条件、はみ出し検査、本文の自動行送り（`bodyLeadMode` の保存契約と旧文書の互換）。
